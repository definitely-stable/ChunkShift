Original CSM SHA and reader source identical across OS/replicates.

**Key falsification of a naive B2A memory baseline:** on Linux with ZERO held reader, switching internal sampling ON rather than OFF increases externally measured sampled resident high-water by **+17.864 MiB (r0) and +17.824 MiB (r1)**. Original target managed-heap-after-idle is ~11.96 MiB (ON/0) versus ~1.01 MiB (OFF/0), a roughly 11 MiB difference. With 16 held reader, the analogous peak difference is +17.660 / +17.375 MiB. Thus the B2A high 30+ MiB Linux sampled peaks must not be attributed to Core reader ownership or used as native product memory budgets.

**Windows contrast:** ON-OFF with zero held reader is +0.696 / +0.402 MiB; with sixteen held reader ON sampled peak is actually lower than OFF by about 0.320 / 0.257 MiB. Windows managed heap is ~1.15 MiB higher with internal sampler ON. Platform trimming, runtime and separate-process measurement noise prevent using one uniform observer overhead constant or claiming that negative Windows sampled peak deltas are genuine memory savings.

**Reader effect under external-only baseline:** With internal sampler OFF, held16 versus zero reader sampled peak difference is **+3.656 / +3.453 MiB Linux** and **+3.430 / +3.355 MiB Windows**, but the target cases are sequential **separate fresh OS processes**; their maxima are not matched within-process causality and include CLR initialization/GC/OS noise. They demonstrate a repeatable signal, not a per-reader exact constant or release RSS upper bound.

## Interpretation, method recommendation and remaining blockers

This slice **qualifies a cleaner measurement approach**, not a product candidate: future baseline resource calibration should use a *separate native observer process* and **no in-target high-frequency sampling** for primary resident high-water. Keep in-target allocations/GC instrumentation separate from peak-RSS trials, and add observer-on/off measurements if making a strict release memory claim. Even external /proc smaps or PSAPI calls have OS and CPU cost and sampled maxima are not instantaneous hard upper bounds.

The fixed r0/r1 reversed order helps expose time/runner drift but **is not randomization**, and two host replicas per OS cannot create a prospective noninferiority confidence bound. The synthetic corpus (BLAKE3/BIDX only), non-production Plan, SHA256, real-versioned calibration, Windows 300-second trimming, AOT, and lazy/hybrid2 hardened CPU costs remain outside scope. Historical Core 0.1.1 E3 DEFER and original R0 decisionRunsAllowed=false, budgetsLocked=false remain unchanged; no R3 sealed holdout or numerical adoption threshold.

**Disposition:** E3-R2-B2B EXTERNAL_OBSERVER_CALIBRATION_PASS / PRODUCT_NOT_QUALIFIED / NO_ADOPT. Next E3-R2-C: use external native observer for broader *unsealed real-versioned* CSM + public Plan, independent Windows/Linux CPU/JIT and memory acceptance sensitivity, then prospectively review and freeze numeric product budgets **before** any separate decision holdout.
