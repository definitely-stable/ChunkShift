## Frozen versioned pair, not source-free

Base content is deterministic SplitMix64 `0xC4855A112026`;
target clones base and flips 1,024 consecutive bytes at midpoint.
Default FastCDC 64-KiB profile, BLAKE3, BIDX enabled. For each 1/8-MiB
size, all four operations use **identical physical base CSM, target CSM,
and CSP patch** (real bytes SHA checked by the independent evaluator).
The corpus has strictly positive both reused and missing chunks.

All fixture preparation, preliminary PatchPlan and CSP Create oracles,
and warmup occur outside timing. Two in-memory manifests are verified
by public API in `verify-pair`. Actual public `ChunkPatch.PlanAsync`
also traverses both manifests and builds base/target ID sets.
`ChunkPatch.CreateAsync` reads in-memory content and tests the
**physical CSP bytes on every call** (validation overhead is included).
`ChunkPatch.ApplyAsync` publishes a real target **disk file**, checks
public target ManifestId on every call and SHA-256 of published bytes
after each timed round. All source payloads are **intentionally live**:
post-GC RSS is **not comparable** to G1-E metadata-only/source-free RSS.

For `PlanAsync` only, source inspection confirms **exactly two**
`ManifestReader.OpenAsync` calls (one base, one target) on its normal
success path. G1-D isolated one **147,528-byte LOH tick**
per `CsmStreamReaderCore` allocation; the reader buffer element capacity
is 147,500 bytes. The hypothetical upper bound on **gross removed
managed allocation** from eliminating both arrays is
`2 × 147,528 = 295,056 bytes` per Plan invocation:

| Plan fixture | Median allocation / call | Hypothetical eliminated fraction |
|---|---:|---:|
| 1 MiB | 396,768 bytes | **74.36%** |
| 8 MiB | 411,246 bytes | **71.75%** |

These percentages assume **zero replacement allocation cost** and
ignore any lifetime/pooling side effects. They are an allocation
**ceiling**, not real savings and absolutely **not an Amdahl CPU
speedup bound**. It remains necessary to sample call stacks/in-path
CPU before claiming end-to-end runtime value. There is no analogous
certified two-reader count for create/apply in this run; the ~7.4-MiB
create allocation already shows that a CSM-only optimization cannot
address the complete operation's allocation picture.

## Important limitations and interpretation

1. **Do not subtract** `verify-pair` batch time from `PlanAsync`
   to infer CSM CPU share. These are different full public operations,
   not an additive call tree. Small few-millisecond batch times on a
   shared hosted runner have uncontrolled scheduling/JIT effects.
2. The two 1/8-MiB pairs each contain exactly **one missing chunk**:
   deliberately realistic API flows and error contracts, but not a
   representative production patch-size or compression distribution.
   Create/apply need broader corpora before any production conclusion.
3. Apply includes actual temporary file creation and atomic rename
   semantics; the 8-MiB first measured batch was 217.656 ms versus
   ~76–88 ms for later rounds. Disk cache/setup can dominate; the
   median is descriptive only.
4. Create includes a nontrivial byte-level patch oracle; do not claim
   it measures isolated internal encoder time. The `Gen2` differences
   (create 13 at 1 MiB, 2 at 8 MiB) reflect process/GC scheduling
   and cannot certify specific object ownership or memory leak.
5. Last-GC LOH footprint is not LOH allocation volume. Process RSS
   includes fixtures and possibly previous scratch publication; it
   is not per-reader peak retained memory.
6. A `ArrayPool<byte>.Shared` request of 147,500 bytes can occupy
   a 262,144-byte bucket, so lower allocation churn alone is not
   sufficient evidence to enable pooling.

## Next research decision

G1-F's **product allocation gate passes for PlanAsync**: there is a
potentially material gross reader-buffer allocation budget (72–74%)
within the frozen synthetic Plan workload. It is **not** a product
optimization verdict or proof of speedup. A new preregistered
**G1-G Plan-specific laboratory A/B** may therefore compare:

- Current eager max CBLK allocation.
- Lazy read-time exact CBLK payload allocation with whole-CBLK
  validation before exposing records, including 11/102/5052 entries.
- Bounded pool with measured actual bucket size, post-GC LOH/RSS
  retention, concurrent pressure, stale-state clearing, disposal,
  cancellation and corruption fail-closed validation.

Before shipping production change, require stable paired **PlanAsync
wall/CPU/alloc/GC** evidence across larger real-life input sets and
separate **source/stack CPU attribution**. Inspect the actual production
call pattern instead of fabricating a 16-worker Plan workload.
