## Actual CLR MethodLoadVerbose optimization tiers

Previous G2-C3 had only configuration/timing associations, not method-level JIT observations. G2-C4 captured both `MethodJittingStarted` and `MethodLoadVerbose` from the runtime, with actual `OptimizationTier` values. This distinction is critical: `MethodFlags=Jitted` does **not** identify the tier.

For no-warmup child processes, the complete method-load tier counts were:

| Runner | Tiered Compilation | `QuickJitted` | `Optimized` | Tier1 during 0-warmup run |
| --- | --- | ---: | ---: | ---: |
| Lane 0 / Xeon 8370C | OFF | 0 | 335 | 0 |
| Lane 0 / Xeon 8370C | ON, PGO OFF | 461 | 99 | 0 |
| Lane 0 / Xeon 8370C | ON, PGO ON | 460 | 99 | 0 |
| Lane 1 / Xeon 8573C | OFF | 0 | 338 | 0 |
| Lane 1 / Xeon 8573C | ON, PGO OFF | 461 | 99 | 0 |
| Lane 1 / Xeon 8573C | ON, PGO ON | 460 | 99 | 0 |

These are observed JIT method publication events, not counts of all executable/native methods; ReadyToRun, native precompiled code and inlining require separate treatment. They **directly demonstrate** that TieredCompilation ON generated many `QuickJitted` methods whereas TieredCompilation OFF emitted `Optimized` for this instrumented workload.

For **64-prewarm** traces, lane 1 provided additional actual tier publications:

- `tiered-pgo-off`: **2 `OptimizedTier1`** loads, including `Blake3.Blake3ManagedCore.Mix`. The `Mix` event occurred **after the last measured call 32**, not during the early latency phase.
- `tiered-pgo-on`: **14 `QuickJittedInstrumented`** + **7 `OptimizedTier1Instrumented`** additional loads. The instrumented set includes `Blake3.Blake3ManagedCore.Mix`, `RotateRight16/12/8/7`, `DiagonalizeSse41`, `UndiagonalizeSse41`, `PermuteMessageAndRoundSse41`, `ChunkShift.Manifest.ManifestIdAccumulator.Append`, `ThrowIfUnavailable`, and physical CSM `CsmParserMath.Add`. Many of the seven Tier1 publication events were recorded **at call 32**; some after. This does *not* establish a latency drop caused by their publication.
- In lane 0, no `OptimizedTier1` or instrumented tier upgrades were observed within these limited traced processes, despite the identical managed target binaries.
- MethodLoadVerbose publication is a completion event, not the earlier call-count threshold decision or proof that subsequently executed instructions selected that version. EventPipe tracing itself perturbs execution.

## Decision gate and end of slice

**Confirmed:** a real EventPipe capture pipeline works on GitHub-hosted Linux without administrator privileges; actual CLR `QuickJitted`, `Optimized`, `QuickJittedInstrumented` and `OptimizedTier1` names can be captured with per-call timestamps; particular BLAKE3 and ManifestId methods do have tiered/instrumented versions under some configurations; original CSM identity, source absence and marker timing all passed.

**Not confirmed:** the exact method/tier causing the original G2-C2 ~24ms / ~6–9ms variance, causality of the G2-C3 call-22 transition, cross-platform product performance improvement, memory-benefit acceptance, or the value of adopting ManifestId batching.

**Verdict: `TRACE_CORRECTNESS_PASS / TIER_EVENT_PRESENCE_CONFIRMED / ORIGINAL_PHASE_CAUSE_UNPROVEN / NO_PRODUCT_VERDICT`.** The research trace artifacts should be merged only after full PR CI and code review; retain the unchanged production `ManifestIdAccumulator`. A next investigative step is optional only with a **new frozen, narrowly scoped threshold for stopping** (e.g., direct EventPipe+MethodFlags/JIT disassembly for the same hardware) and may still be inconclusive; *do not* consume another general 384MiB/large-runner campaign to reselect staging widths using this data.
