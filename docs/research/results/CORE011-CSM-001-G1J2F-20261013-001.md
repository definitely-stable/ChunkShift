## Five preregistered Core kernel chunking lanes

The production Core presently registers **only** `fastcdc.gear.chunkshift.v1.64k`, at (min/target/max) = **16/64/256 KiB**. Names such as `fastcdc.v1.patch64k`, `fastcdc.v1.general256k` and `fixed.v1.*` are NOT supported public profile identifiers in this build. The other four profiles below were executed using **internal existing Core kernel** exclusively from the benchmark project, without registering or serializing any new public CSM ProfileId. Each of ten scans (five lanes × both original DLLs) was compared **tuple-for-tuple** against `ChunkingReference.Chunk` on the same original bytes; stable also matched public `ChunkScanner.ScanAsync`.

Exact full target byte reuse from FastCDC16k **149,568 / 6,697,264 = 2.2333%**. This is a direct, byte-verified lab result, not a patch-size saving. For all target `ChunkId` hits, **entire original base and target source byte slices were checked for equality**, not just 256-bit hash matches. Their source scan offsets and lengths are preserved in original TSVs; consolidated [eight exact matches CSV](data/CORE011-CSM-001-G1J2F-20261013-001/fastcdc16k-matches.csv) and [all five aggregates CSV](data/CORE011-CSM-001-G1J2F-20261013-001/profile-aggregates.csv).

Seven consecutive FastCDC16k target chunks (#259–265 inclusive) are identical to seven consecutive base chunks at a constant byte offset difference **+78,221** (target–base), totaling **123,909 bytes**. The eighth matching target chunk #313 has length **25,659** bytes and offset difference **+93,339**. The first preserved run is therefore not merely eight scattered hash coincidences: it is a shifted exact contiguous byte region whose internal canonical FastCDC16k boundaries stabilize after relocation. However, this observation alone does not identify which CLR metadata/IL/RVA changes caused the offset shift.

## CBLK records / overhead, and what it does NOT measure

`CBLK` entry + envelope estimate only: `36 * chunkCount + 44 * ceil(chunkCount / 4096)`. The byte estimate is for 32-byte ChunkId, 4-byte length, CBLK header/prefix/CRC. **It explicitly excludes** CORE, CEND, BIDX, FOOT, trailer, CSP payload, compression, pack indexes, transfer headers, and CPU/GC.

| Lane | Base CBLK-only estimate | Target CBLK-only estimate |
|---|---:|---:|
| stable-fastcdc64k | 2,708 B | 2,960 B |
| lab-fastcdc16k | 11,384 B | 11,420 B |
| lab-fastcdc256k | 728 B | 764 B |
| lab-fixed16k | 14,588 B | 14,768 B |
| lab-fixed64k | 3,680 B | 3,752 B |

Target FastCDC16k requires **235 additional chunks** relative to stable64k and **8,460 additional target CBLK record/envelope bytes**, a **3.86×** CBLK-only increase. This does NOT imply patch cost grows or shrinks by 8,460 B; CSM metadata is not interchangeable with the actual patch wire bytes. Actual supported physical CSM sizes (3,098/3,350 B) are known **only for stable profile**, and production API currently does **not** support creating a valid canonical CSM for the other lanes.

## Interpretation, limitations and next test

This is the first **positive exact full-chunk reuse result** in the J2B→J2F Roslyn line, under an explicitly preregistered smaller FastCDC configuration. The earlier J2E finding that no whole *original stable64k* chunk is preserved remains true: J2F newly emits **different, smaller boundary-defined chunks** from unchanged subregions and recovers eight of them.

It does **not** prove end-to-end CSP patch savings or a superior production default, nor does it imply all binaries benefit. Two alternative constraints remain: one real version pair only, and no representative mixed-reuse multi-CBLK reader workload (all scanned manifests are small; only stable profile produces real physical CSM). There is no independent held-out version pair, reconstruction verification under any hypothetical new wire profile, CPU/GC calibration, or complete patch cost comparison.

**Follow-up:** freeze a same-family **held-out** independent real NuGet pair to test if FastCDC16k's exact reuse generalizes, and separately design a bounded lab-only CSP patch-size/reconstruction comparator without inventing a CSM public profile ID. An alternative experiment could isolate the source/target bytes around the 123,909-B shifted exact run, map changed CLR offsets and test reversible patch transforms with exact inverse proofs (issue #221). No post-hoc addition of profiles to this J2F result.
