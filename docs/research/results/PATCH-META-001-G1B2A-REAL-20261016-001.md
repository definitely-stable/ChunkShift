These per-sample worker stopwatch intervals **can overlap** under H2-W2. The search-share ratio is descriptive, not a validated causal speedup ceiling; instrumented latency and search measurements have different accounting bases. In particular, the (probe on − probe off) wall differences cannot be attributed to instrumentation overhead causally with only four warm samples per mode and different new child process/JIT/scheduling effects. No cache lookup, serialization, content hash revalidation or sidecar I/O occurs.

The significant result is the *orders-of-magnitude gap*: the consumed production offset-candidate enumeration does not contribute anywhere near the issue #220 30%-savings target on this original .NET release pair. Adding persistent per-offset cached search lists would introduce lookup, bytes and invalidation costs to avoid less than a millisecond of summed worker time per ~10-second build. That **narrow hypothesis** is strongly disfavored by this pilot, but the result must not be generalized to unrelated workloads or a different costly derived feature.

The full base/target manifest observations are saved in stage JSON. Manifest timings are **mixed mandatory verification + materialization** and therefore cannot be counted as 100% reusable. Required source SHA-256, target chunk verification, base dictionary integrity checks, zstd encoding, CSP payload output and manifest validity must remain authoritative and are excluded from any META speedup estimate.
