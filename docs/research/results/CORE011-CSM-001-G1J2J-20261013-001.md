## What was really measured

Two original pre-existing, independently SHA-frozen original managed binary pairs: Roslyn `Microsoft.CodeAnalysis.CSharp.dll` 4.13.0→4.14.0 and independent Newtonsoft.Json DLL 13.0.2→13.0.3. Each pair was processed with exactly two profiles: unchanged registered stable64k and a disposable detached Core build that advertises **its own distinct** `lab.fastcdc.gear.chunkshift.v1.m4096.t16384.x65536` identity/fingerprint. Both `based` and `standalone` CSP modes were measured. Every physical CSP SHA-256 and length matched the original J2I artifact #11810882204 byte-for-byte; every CSP applied to exact original target DLL SHA-256 and full CSM content `verify` PASS.

The independent Python CSP v1 reader decomposed each physical byte, checked PAYL/PIDX CRC32C, absolute index offsets/metadata, FOOT offsets and exact embedded physical target CSM, and checked against the public `PatchInfo` length, stored payload bytes and entry counts.

**Exact conservation:** `PhysicalCspBytes = preamble + section headers + TCSM bytes + BASE ID + PAYL 16-byte prefixes + PAYL 40-byte entry headers + PAYL 32-byte dictionary refs + stored encoded payload + PAYL CRC + PIDX prefix + PIDX 24-byte records + PIDX CRC + FOOT 56 bytes + TRAILER 64 bytes`. Exact equality for all 8 original files, not a regression/estimate.

### PAYL/codec observations on real with-base patches

| Field | Roslyn stable64k | Roslyn lab16k | Newtonsoft stable64k | Newtonsoft lab16k |
|---|---:|---:|---:|---:|
| PAYL entries | 81 | 308 | 10 | 31 |

| Raw stored bytes | 0 | 0 | 0 | 0 |
| zstd entries without dictionary | 17 | 95 | 0 | 0 |
| zstd entries with dictionary | 64 | 213 | 10 | 31 |
| zstd bytes without dictionary | 387,552 | 561,575 | 0 | 0 |
| zstd bytes with dictionary | 855,716 | 843,149 | 75,617 | 74,616 |
| **Total stored bytes** | **1,243,268** | **1,404,724** | **75,617** | **74,616** |

**Roslyn:** The 16k candidate reuses 8 complete chunks, but its total stored compressed payload grows **+161,456 B**, a majority of the physical loss. Its changed set of chunk boundaries yields more payload entries, zstd frames and dictionary IDs. One cannot recover this extra payload cost by removing only manifest/PIDX overhead; a hypothetical causally optimized candidate selector is not measured.

**Newtonsoft:** 16k reuses 5 complete chunks and actually stores **1,001 B fewer** encoded bytes. But +840 B entry headers, +2,720 B dictionary ref IDs, +504 B PIDX records and +956 B embedded CSM exactly total +5,020 B, overriding the 1,001-B payload reduction and causing a **4,019 B larger patch**. The result pinpoints actual per-entry metadata cost, rather than attributing a guessed number to a generic container header.

**Standalone controls:** No dictionary reference IDs occur, but lab16k is still worse due to changed encoded payload sizes and more entries/CSM/PIDX. This is an essential negative control against saying all loss is caused by dictionary references.

## Limits and next permissible research

This accounting is deterministic and reproducible on the two selected SHA-frozen managed DLL pairs, but is not a statistically independent population estimate or a proof of universal FastCDC64k optimality. Splitting stored bytes by codec and dictionary presence **does not causally attribute compression improvement to dictionary candidate search or establish compute non-inferiority**. The original J2I whole-CLI process times remain descriptive with startup, shared runner scheduling and I/O noise.

* The existing stable64k default is unchanged; lab16k never becomes a public `ProfileId` or production format commitment.
* No `src/`, public API, CSP/CSM wire schema or default update in either implementation or evidence PR.
* #154's CSM reader allocation/pooling performance qualification remains an independent blocked gate requiring a real multi-CBLK mixed-reuse product corpus and calibrated numerical thresholds.
* Next source-justified research should **pre-register** controlled time attribution for baseline encoder dictionary-candidate enumeration/selection and zstd work, without using these two already-examined pairs to tune an eventual general product strategy. Broader genuinely independently selected corpora would be needed for a new production adoption decision.
