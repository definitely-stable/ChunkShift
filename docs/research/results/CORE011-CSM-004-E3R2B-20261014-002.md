## Physical private resident memory — point-in-time (MiB)

Measured after 30 seconds natural idle (short and large CSM) and after 300 seconds (large CSM). **0 and 16 are separate fresh OS processes, not same-process before/after.**

| OS | Source MiB | Idle | 0 held readers | 16 held readers | Separate-process difference |
| --- | ---: | --- | ---: | ---: | ---: |
| Linux | 1 | 30 s | 12.488 | 12.969 | +0.481 |
| Windows | 1 | 30 s | 6.047 | 6.547 | +0.500 |
| Linux | 384 | 0 s | 13.898 | 16.500 | +2.602 |
| Windows | 384 | 0 s | 7.340 | 10.062 | +2.722 |
| Linux | 384 | 30 s | 14.105 | 16.715 | +2.610 |
| Windows | 384 | 30 s | 7.488 | 10.117 | +2.629 |
| Linux | 384 | 300 s | 14.270 | 16.891 | +2.621 |
| Windows | 384 | 300 s | 2.707 | 2.750 | +0.043 |

On Linux at 300 seconds, additional private resident pages across the held-vs-control fresh processes amount to about 2.621 MiB /16 = approximately 168 KiB per live partially read eager reader. The known eager 147500-byte CBLK buffer plausibly explains most of the difference but the remainder includes reader metadata, memory page rounding, CLR and host process noise. **This is not a causal point estimate and not a production RSS upper bound.**

On Windows, both control and 16-held **private working sets decrease sharply** between 30 and 300 seconds. Despite 16 still-live readers, private resident difference falls to about 0.043 MiB, while the underlying memory **is not released**:

| Windows large CSM, at 300 s | Control 0 readers | 16 held readers |
| --- | ---: | ---: |
| PSAPI PrivateWorkingSetSize | 2.707 MiB | 2.750 MiB |
| PSAPI PrivateUsage (private committed bytes) | 10.555 MiB | 13.129 MiB |
| GC.GetTotalMemory(false), managed heap snapshot | 1.630 MiB | 4.277 MiB |

The combination of still-held strong reader references, unchanged large private commit difference and managed heap difference is consistent with idle working-set trimming / eviction on Windows. **It does NOT establish that 16 eager CBLK arrays were deallocated.** The specific trimming trigger is not proven. Thus a decision based on Windows 300s PrivateWorkingSetSize alone would hide live CLR managed buffers. Report resident and committed memory together; do not infer freed objects from nonresidency.

## Scientific limitations and next step

**Disposition:** E3-R2B1 RESIDENT_BASELINE_CALIBRATION_PASS / PRODUCT_NOT_QUALIFIED / NO_ADOPT. Zero product candidate experiments; R0 stage remains preregistration, historic CORE011-CSM-004 Core 0.1.1 DEFER unchanged; no numeric budget locked.

This is a synthetic BLAKE3/BIDX-only **eager** calibration on **one Windows host and one Linux host**; each control/held-16 pair is a different process subject to CLR/JIT and host noise. Memory snapshots are not private-resident high-water tracking. There is no 64-reader stress, Windows ARM64, NativeAOT, paired product Patch.Plan, SHA256 suite, or real-versioned predecision calibration. 300s Windows working set divergence underscores OS-specific paging uncertainty. It is invalid to divide one cross-process delta by 16 to establish an exact per-reader causal law or use either single runner as a release threshold.

**Next E3-R2-B2:** independent replicated Linux and Windows memory/CPU blocks including true private-resident high-water trace, OS memory pressure/working-set trimming provenance, representative unsealed real-versioned CSM and public Plan, net8/net10/AOT constraints, and CPU/JIT host metadata. Only *after* independent review should a prospective separate numerical decision freeze and sealed holdout be created. E3-R3 decision is forbidden today.
