## Observations, not an optimization verdict

Operation: public **manifest-verify**, one fresh process per 1- or 16-worker lane, 3 timed rounds, **4 operations per worker per round**. A custom trace provider marks warmup completion, each round start/end, and a separate 32 × 131,072-byte post-retention positive control. All trace events for fixture creation are explicitly excluded.

- **0 EventPipe dropped events**, all **9 mandatory phase markers** in each case.
- Positive control: exactly **32 LOH ticks**, `System.Byte[]`, in each lane.
- Static reader path allocates `CsmStreamReaderCore._blockBuffer` exactly once per reader: `new byte[SectionHeaderSize + MaximumCblkPayloadSize]`, capacity **147,500 element bytes**, before reading blocks. For the observed arrays the corresponding LOH tick amount is **147,528 bytes** (accounting for runtime object overhead/alignment), which agrees with the per-call trace signature.
- This buffer is **per-reader, not per-CBLK**: crossing 4,096 chunks does not allocate an additional buffer for each CBLK. The 1-MiB smoke with just 11 chunks likewise produced four LOH `System.Byte[]` ticks in four metadata-reader calls. Thus **the boundary itself is not a demonstrated trigger for LOH allocation**. The multi-CBLK scenario establishes realistic reader validity and scale.
- After timed rounds and **before** the positive control, separately forced GC showed **managed bytes 811,456 / 838,352**, and **last-GC LOH size 1,166,408** for 1/16 workers. These are only post-GC snapshots; they cannot independently name the retained objects.
- GC generation 2 collections remained at zero in 1-worker rounds and totaled **8** for 16 workers. `maxActive` was only 4–5 despite 16 scheduled workers, so no claim of 16 simultaneously executing CPUs is warranted.
- Do **not** compare traced wall time to untraced pilot wall time: tracing overhead and shared hosted CPU scheduling are uncontrolled.

## Important correction to initial trace run

The **initial** successful diagnostic run
[#38198074881](https://github.com/definitely-stable/ChunkShift/actions/runs/38198074881)
put the 32-array positive control *before* post-GC retention. Its trace allocation windows were valid, but its retention sample was contaminated and excluded. The current documented run #38198319677 moves the positive control **after** retention; do not use the earlier retention figures.

## Trace integrity, sampling caveats and source identification

`GCAllocationTick` events are **sampled**: `AllocationAmount64` is an interval amount since the preceding tick, and `TypeName` names the triggering allocated object, **not ownership of all bytes in the interval**. A `System.Byte[]` type is not a CBLK stack trace. The close correspondence of observed event count (one/call), size (147,528), source reader array capacity (147,500), and short-manifest smoke is strong evidence for a **fixed-capacity per-reader LOH buffer**, not yet an independent call-stack proof. Buffer escape/retention lifetimes remain unmeasured.

All measurements came from unchanged public CSM APIs, no production CSM patch, no NuGet/API change, and no altered persisted CSM physical identity.
