## Frozen candidate and pool size verification

The G1-H source-hashed variant of `CsmStreamReaderCore` starts with
`_blockBuffer=[]`. It allocates a small exact-size reader-owned
array if the validated `CBLK recordLength <=81920` bytes, without
touching the nested static pool. For larger CBLKs it rents from
`ArrayPool<byte>.Create(maxArrayLength:147500,maxArraysPerBucket:4)`,
returns the array only once on idempotent Dispose, and clears the
rented array on return. CRC32C, semantic/overflow validation and
no-entry-exposure-before-entire-CBLK-verification remain unchanged.

`a62772638c715005cb8a1a6ca58222349755a7e21a341ff80655a825910cebf2`.
**No candidate changes were committed to production `src/`.**

The independent .NET pool probe measured four simultaneous
`Rent(147500)` calls from `ArrayPool<byte>.Create(147500,4)`:

- requested size: **147,500 bytes**

This direct bucket measurement is not an ownership trace of the
reader's private static pool; its actual residency is independently
estimated through post-full-GC process managed heap, which includes
other objects.

## Actual public-operation measurements

All rows are median process managed allocated bytes **per completed
public API call**, KiB, over five measured batches, **not per-object
bytes**. `PlanAsync` used identical deterministic BLAKE3/BIDX
1MiB and 8MiB changed version pairs with 1 missing chunk and exact
public Plan/physical CSP and CSM SHA oracles. Public metadata
verification used source-free 1MiB/11-chunk and 384MiB/5052-chunk,
**2-CBLK** CSM with pinned physical SHA
`342ff5e8175304be3f27873fdfeee051deaa0d3697d60e1dcdc3799e674eac2a`,

### Measured idle managed-heap retention

**Post-explicit-GC process managed bytes**, **not** the number of
reader-owned large arrays, GC allocation volume or peak RSS:

| Source-free verify | Eager | Lazy | Pool4 | Hybrid |
|---|---:|---:|---:|---:|
| 1MiB w1 | 402,608 | 399,464 | **663,160** | **402,680** |
| 384MiB w1 | 587,496 | 584,208 | 848,024 | **848,096** |
| 384MiB w4 | 595,784 | 594,936 | 1,645,208 | **1,646,224** |
| 384MiB w16 | 601,968 | 601,872 | 1,652,216 | **1,652,328** |

Critical: **hybrid preserves short-only reader memory profile**
(402,680 vs eager 402,608 B, +72 B under source-free 1MiB w1),
where `pool4` retains +260,552 B. Once a large CBLK is read,
hybrid retains roughly the **same +1.05MiB** as pool4 at 16-worker
pressure, not better idle memory. Therefore hybrid is not a
universal solution to the large-pool retention trade-off.
The ~1MiB premium is consistent with four 262144-byte rented
bucket arrays, but per-array lifetime attribution has not been
observed directly inside reader private pool.

## Counterbalanced A/B/A Plan evidence

Two separate process sequences per source size:
`eager→hybrid→eager` and `hybrid→eager→hybrid`,
five rounds × eight Plan operations per position, each position
with a distinct RunId and full identical source/CSM/CSP oracle.

| Plan input | Sequence | Eager median batch wall ms* | Hybrid median batch wall ms* | Descriptive difference |
|---|---|---:|---:|---:|
| 1MiB | E-H-E | 0.7736 | 0.6792 | −12.20% |
| 1MiB | H-E-H | 0.7823 | 0.68485 | −12.46% |
| 8MiB | E-H-E | 2.3522 | 2.2262 | −5.36% |
| 8MiB | H-E-H | 2.3143 | 2.25935 | −2.37% |

\* Repeated E or H positions are **averaged from their two
five-round medians** within one sequence, not combined into a
single statistical latency distribution. All observations are
**batch wall**, not per-request latency or causal CPU Amdahl.

Both sequence orders observed lower hybrid batch wall under
this **single runner and two tiny version-pair corpora**. The
small 0.7–2.4ms batches remain vulnerable to scheduling, warm-cache,
host contention, run order and physical frequency drift. No
randomized independent hosted runs, CPU sampling attribution,
confidence intervals, p95, production-level throughput or general
speedup guarantee exists yet. Do not issue production ADOPT based
on this measurement.

## Recommendation / next gate G1-I

**G1-H feasibility PASS:** full parser/vector correctness under
the selected test suite; tangible and consistently large measured
allocation reduction, direct 256KiB pool bucket confirmation and
explicit short-vs-large retention split. **Adoption NOT ready.**

The next experimentally justified work is a **bounded retention
policy**, not another blind pooling switch:
- compare hybrid `maxArraysPerBucket=1/2/4`, versus a reader-local
  reusable buffer or idle-trim alternatives. Measure pool contention,
  re-rents and CPU work under sustained 1/4/16 and (only after harness
  extension) 64 workers. Do not assume four retained arrays is the
  optimal number.
- Independent GitHub-hosted repeat-run randomization across days/
  runners, longer end-to-end Plan iterations and real changed-file
  corpora; direct CSM source/stack CPU attribution instead of
  subtracting different public API times.
- Full release matrix: Windows, AOT where supported, broken/truncated
  streams, CRC failures, cancelled/partially consumed reader and
  disposing multiple times under concurrent load. The current
  selected 254 tests per target framework do not prove exhaustive
  behavior across all possible inputs.
- Freeze thresholds for acceptable memory after idle GC and
  allowable CPU regression before any public default change.
  Header range and pre-exposure CRC checks must remain semantically
  identical; never allow a stale pooled array to leak into records.
