## Exact-window comparison (shift-independent target search)

Base anchors are **every 256 bytes**; target is searched at **every byte offset**. Rolling polynomial hashes `257 mod 2^64` are only an accelerator: every candidate must match the actual original bytes. Count matching base anchors only once even if the target contains repeated matching windows. Byte coverage is the **union** of matched source windows, not the sum of overlapping windows.

| Window | Base sampled windows | Verified matching base windows | Base exact-window coverage lower bound |
|---|---:|---:|---:|
| **4 KiB** | 25,782 | **2,069** | **798,464 B** |
| **16 KiB** | 25,734 | **634** | **291,328 B** |
| **64 KiB** | 25,542 | **275** | **135,680 B** |

Each match was in source PE `.text`. The base 4-KiB anchored match coverage is **at least 798,464 / 6,604,072 ≈ 12.1%** of the source bytes. For 16 KiB it is ≈4.4%, and for 64 KiB ≈2.1%. This does **not** mean those fractions are directly reusable as identical FastCDC chunks, patch savings or a lower bound on a production patch.

Examples of verified shifted exact-window matches (base → target file offsets):

- 4 KiB: `672000 → 680360` (offset shift +8,360 B)
- 16 KiB: `4917248 → 4988806` (offset shift +71,558 B)
- 64 KiB: `5459968 → 5538189` (offset shift +78,221 B)

A deliberately coarser control found **zero** target 4-KiB `offset % 4096 == 0` fixed blocks identical to any base block on that same 0-aligned grid, even though the exhaustive-offset search found 2,069 exact 4-KiB anchored matches. This isolates strong positional sensitivity in the *fixed-block control*, **not** proof that FastCDC has a bug or would recover these windows after normalization.

## PE/CLR layout observations (descriptive, not causally established)

Both binaries have PE `.text`, `.rsrc` and `.reloc` sections with a valid mapped CLR header.

| Section | Base raw offset / length | Target raw offset / length | Same relative-section-position equal bytes |
|---|---|---|---:|
| `.text` | 512 / 6,590,976 | 512 / 6,684,160 | 696,320 |
| `.rsrc` | 6,591,488 / 1,536 | 6,684,672 / 1,536 | 1,482 |
| `.reloc` | 6,593,024 / 512 | 6,686,208 / 512 | 508 |

At the **same full-file byte offset**, 696,925 of the first 6,604,072 bytes were identical (≈10.55%). By contrast, allowing shifted searches finds substantial additional **contiguous** unchanged windows. Small resources/relocation sections are relatively similar internally, but their own sizes are below the 4-KiB window threshold.

These are raw PE sections, not decoded IL bodies, tables, RVA operand patch-sites, or a verified reversible `.NET-aware` transform. Do not infer that IL/RVA normalization would automatically preserve, restore or accelerate these exact bytes.

## Interpretation and next gate

The earlier **public `ChunkPatch.PlanAsync`** on these exact raw binaries gave **`ReusedChunks=0`, `MissingChunks=81`** and one CBLK per DLL, from original J2C. The new **independent** byte comparison has now shown at least 798,464 bytes of contiguous 4-KiB anchored windows in the base that appear exactly in the target at potentially different offsets.

Therefore **“no identical CDC chunks” does not entail “no unchanged windows”**. It is an empirical distinction for this specific Roslyn pair, not an error proof. No claim about genuine reusable CSM chunks, byte-normalization gain, or CPU benefit is justified yet.

**Next specific allowed research:** G1-J2E — extract the **actual CSM v1 chunk `(offset,length,ChunkId)`** sequences from the *already frozen* physical base and target manifests, map J2D matched base windows against those chunk intervals, and classify exactly where canonical FastCDC boundaries diverge. Use an independent semantic oracle to distinguish shifted boundaries, unequal length, hash-suite mismatch, or changed chunk content. In particular, seeing a 64-KiB exact window does not prove a whole source CDC chunk is included in it. Record original hashes and failure modes; no production changes.
