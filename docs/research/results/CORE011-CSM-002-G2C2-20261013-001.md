### Allocations: threshold hypothesis versus lingering large-buffer cost

All allocation values are approximate managed bytes **per full public call** across the three rounds (includes harness, not separately isolated kernel):

| Fixture and API | Baseline | Gate-stage64 | Gate-stage256 |
| --- | ---: | ---: | ---: |
| Short 11 BLAKE3 / Verify | 169,580 | 170,301 | 169,857 |
| Short 102 SHA256 / Verify | 169,783 | 169,771 | 169,969 |
| Multi 5052 BLAKE3 / Verify | 170,088 | 172,731 | 179,405 |
| Multi 5052 SHA256 / Verify | 170,088 | 171,971 | 179,328 |

**Lazy-array correctness holds:** short CSM no longer incur the extra 2,304/9,216 data-byte arrays, and measured allocations are in roughly the same 170-KB range. This does **not** imply zero incremental object footprint: two additional private fields and harness/probe noise can still affect allocations. For long manifests staging still costs ~2–9 KiB per call, as expected. The ~147.5-KB eager reader CBLK buffer itself remains unresolved and is independent of ManifestId staging. No inference of long-lived idle retained RSS or Gen2 noninferiority can be made from these short samples.

## Disposition and next allowed work

**G2-C2 algorithmic/semantic pilot PASS:** validated byte-stream identity and lazy staging threshold at 257 on both suites, four genuine CSM fixtures, negative CBLK exposure oracle and both target frameworks. **Performance/release: NO_PRODUCT_VERDICT / NO_ADOPT.** The substantially different BLAKE3 timing regimes and short-runner variance weaken any apparent CPU gain; do not advance this candidate to main production or tune the threshold using the same samples. The original 0.1.1 `CORE011-CSM-002=DEFER` remains and `core011-csm-g1j-contract.v1.json` still has `decisionRunsAllowed=false`, `budgetsLocked=false`.

**Next decision on research direction:** before allocating more large-content runs, isolate the source of BLAKE3 multi-CBLK instability with tightly controlled independent hosted comparators (same exact source-hashed binary and payload, CPU/perf counters where available, steady-state distribution with calibration), AND review whether CPU improvement outweighs extra managed allocations. A later true production decision requires preregistered CPU/wall/alloc/RSS budgets, cross-platform independent runners, real versioned holdouts, public Create path and concurrency/error/cancellation tests. If not economically justified, **stop batching research and retain baseline**.
