### Ограничения (важно для оценки достоверности)

1. **Локальная сборка и тесты невозможны.** `global.json:3` фиксирует SDK `10.0.204` с `rollForward: latestPatch` (feature-band lock), а установлены `8.0.425 / 10.0.302 / 10.0.303 / 10.0.401`. `dotnet build`/`test` падают на резолве SDK. Дополнительно sandbox запрещает запись в `bin/` (скомпилированные артефакты). **Следствие: ни один вывод в отчёте не подтверждён исполнением C#-кода.** Всё — статическое чтение + независимые probe-скрипты на Python.
2. **`web_search` недоступен** (нет API-ключа). Внешние факты брались только через `web_fetch`; PDF не читаются. Всё, что не удалось открыть, помечено как непроверенное.
3. **CI-часть проверена косвенно:** аудитор A4 через GitHub REST подтвердил, что run `35889891073` (`head_sha 1b0635d`) завершился `success` — значит, запиненный SDK **в CI резолвится**, проблема локальная.
4. Верификаторы **не были согласны** с исследователями по умолчанию и активно искали ошибки. Итог: **2 находки опровергнуты полностью**, 115 признаны частичными (переоценённая серьёзность, дубликаты, уже принятые решения), **0 остались непроверяемыми**.

## 1. Главный вывод

> **Инварианты ядра держатся. Реальные дефекты — на краях. Настоящая проблема проекта — не в коде, а в (а) доказательной базе и (б) отсутствии продукта.**

Три независимые атаки (A6, A6-опровергатель, мой собственный разбор) не смогли сломать ни одного из заявленных инвариантов:

- **Инвариантность к сегментации чтения** — опровергатель транскрибировал `FastCdcScalar.FindCut` и `ChunkBoundaryState.Scan` в Python с реальными gear/mask-таблицами и прогнал **225 конфигураций** (3 target × 5 seed × 3 корпуса × 5 сегментаций): **0 расхождений**, 0 зацикливаний, guard `payloadLength == CompletedChunkLength` ни разу не сработал. Предварительно воспроизведён checked-in golden vector (12 чанков).
- **Инъективность `ManifestId` и независимость от физики** — пересчитаны `ManifestId`, `FileDigest`, CRC-32C для всех четырёх фикстур; воспроизведена пара «BIDX есть / BIDX нет» с одинаковым `ManifestId` и разным `FileDigest`.
- **Отсутствие неограниченных аллокаций по недоверенной длине** — `MaximumCblkPayloadSize = 147 484` совпадает с реальным payload фикстуры; ни одна аллокация не управляется длиной из файла.
- **Внешние кросс-языковые оракулы настоящие** — Python-генератор CSM побайтово совпадает с C#-энкодером (340/420/147 920/147 976 байт), а обновление gear-хэша (`hash << 1`) сверено с запиненным upstream `fastcdc 5.0.0 v2016/mod.rs` (строки 191, 341-344).
- **Граница pooled-buffer residuals соблюдена** — `ChunkingKernel.cs:129-133` возвращает оба массива без очистки, и `SECURITY.md:44-67` это явно разрешает. Утечка возможна только для кода в том же процессе; это документированное допущение, а не дефект.

**Что это значит практически.** Приоритеты должны быть не «оптимизировать горячий цикл», а:
1. закрыть доказательные дыры, которые являются **условиями закрытия #9** (fuzz, >RAM, независимая верификация негативных векторов, AOT реального пути);
2. закрыть 2 средних дефекта в CSM-верификации (дёшево, до заморозки формата);
3. принять продуктовые решения **сейчас**, потому что после 0.1.0 они становятся breaking changes (прогресс-API, аутентичность, сжатие, анти-rollback);
4. начать давать пользователю ценность раньше, чем закроется тяжёлый гейт #9.

## 3. Подтверждённые дефекты (чинить)

Отсортировано по (влияние × уверенность) / трудозатраты. Все — с указанием, кем подтверждено.

### P0 — исправить до заморозки CSM (#9)

**D1. CSM: обход MUST-reject правил в tail-фазе** — `A2-F01` ≡ `A6-F01`
- **Evidence:** `CsmReader.cs:683-692` — в цикле tail-фазы проверяется только флаг `RequiredSectionFlag`; известные FourCC (`CORE`/`CBLK`/`CEND`) с флагом 0 уходят в ветку «неизвестная опциональная секция» и **молча пропускаются**. Спека `CSM-V1-CANDIDATE.md:52-62` требует обратного: «CBLK before CORE or after CEND», дубликаты CORE/CEND — MUST reject.
- **Доказательство:** опровергатель собрал мутанта из фикстуры (420 → 500 байт, флаги обнулены, trailer/FOOT/FileDigest пересчитаны) и перебрал все проверки ридера — **все проходят**, `IsValid == true`.
- **Почему тесты не ловят:** `ChunkBlockAfterCend_IsFormatError` (`CsmMalformedInputTests.cs:355-368`) вставляет дословную копию записи **вместе с флагом REQUIRED**, поэтому срабатывает generic-путь «unknown required», а не проверка позиции.
- **Severity:** Medium (не позволяет протащить данные — CEND фиксирует totals+ManifestId, FileDigest покрывает байты; нужен враждебный *производитель*). Влияние — интероп/неоднозначность: два соответствующих ридера расходятся в вердикте.
- **Fix:** S — в tail-цикле переключаться по `header.Type` и бросать для `CORE`/`CBLK`/`CEND`; проверку REQUIRED оставить только для действительно неизвестных FourCC.
- **Статус:** подтверждено и опровергателем, и аудитором обоих направлений.

**D2. CSM: `ProfileId` не связывается с `ProfileFingerprint` на manifest-only пути** — `A6-F02` ≡ `A2-F22(3)`
- **Evidence:** `ManifestResultMapper.cs:33-60` **не может** выдать `ManifestVerificationFailure.ProfileSemantics`; `CsmReader.cs:902-904` резолвит только hash suite. Флаг `ProfileSemantics` (`ManifestVerificationFailure.cs:24-27`) документирован ровно для этого случая, но выставляется только на content-пути (`ChunkManifest.cs:90-93`).
- **Влияние:** `VerifyManifestAsync` говорит «valid» для манифеста, чей `ProfileId` резолвится локально, но чей fingerprint ему не соответствует — то есть семантика, по которой потребитель будет re-chunk'ать, не связана.
- **Severity:** Low–Medium (обман только на уровне метки; `ManifestId` связывает fingerprint на `CsmReader.cs:153-156`, content-путь ловит).
- **Ограничение fix:** неизвестные ProfileId **обязаны** оставаться валидными (`CsmGoldenVectorTests.cs:61`), иначе ломаются golden-векторы. Нужно решение + покрытие issue/RFC.

**D3. CSM: ложный флаг «неверный контент»** — `A2-F06`
- **Evidence:** `CsmContentVerifier.cs:80-81` выставляет `ManifestVerificationFailure.Content`, когда контент **доказуемо верен**, а испорчен лишь сохранённый в CEND `ManifestId`. В core-сценарии верификации это ложный отчёт «content mismatch».
- **Severity:** Medium. **Fix:** S.

**D4. CSM: расщепление контракта исключение/результат** — `A2-F05` ≡ `A6-F03`
- **Evidence:** неизвестный, но грамматически валидный `HashSuiteId` бросает `NotSupportedException` из `CsmReader.cs:902-904` (вне `try/catch` на `:889-900`); неизвестный `ProfileId` **проходит** `VerifyManifestAsync`, но бросает из `VerifyAsync` (`CsmContentVerifier.cs:46-48` → `ChunkScanConfiguration.cs:45`). При этом `ChunkManifest.cs:72-75` документирует, что несовпадения профиля — это result-флаги.
- **Severity:** Medium. **Fix:** S — одно явное предложение в документации + тест; **не** переиспользовать `ProfileSemantics` (его документация означает другое).
- **Замечание аудитора:** исправление в формулировке A6-F03 **несовместимо с AGENTS.md/RFC-0001:460-461** в текущем виде.

**D5. CLI: `create f f` уничтожает входной файл (POSIX)** — `A2-F14`
- **Evidence:** `CliApp.cs:67-68` не сравнивает пути; `:110` открывает content на чтение, `:143-146` делает `File.Move(temp, manifestPath, overwrite: true)`, при этом handle ещё в области видимости. На POSIX rename проходит → источник заменяется манифестом самого себя. На Windows — ошибка «файл занят».
- **Severity:** Medium (по мнению аудитора; A2 ставил High) — CLI не пакуется и это sample-Exe, но потеря данных реальна. **Fix:** S.

### 5.2 Стратегический вывод (A5, подтверждён аудитором как «решение, а не дефект»)

> Roadmap относится к **патчу** как к продукту — `RFC-0001:129`: «the first useful product must close the update loop. Manifest and diff are primitives, not the product» — и затем ставит его за гейт, который **явно его не требует** (`ROADMAP.md:48,144`, `PLAN.md:295`, `RFC-0003:41-51`).

Следствие: первая линия совместимости замораживает **субстрат** (CSM, профили, HashSuite, сканер — каждый со строгой candidate-спекой), тогда как **продуктовый артефакт** (CSP) — это 9 строк прозы без владельца. Проект чрезвычайно хорошо подготовлен быть *корректным* и совершенно не подготовлен быть *использованным*.

**Где секвенирование саморазрушительно:**
1. `RFC-0003` откладывает *байтовую раскладку* CSP — правильно. Но он же откладывает *любую пользовательскую возможность reuse/patch* — неправильно, и эти вещи разделимы. План их склеил, поэтому защитимое решение о долговечности формата заодно убрало продукт.
2. Гейт, защищающий это откладывание, необычно тяжёл (10 критериев: независимый верификатор, >RAM streaming, упакованный NativeAOT, bake-off профилей на реальных корпусах). Итог: Core 0.1.0 — **медленная веха, производящая commodity** (FastCDC — опубликованный алгоритм с эталонными портами на многих языках; GEAR-таблица скопирована из `fastcdc-rs 5.0.0`), а дифференциация начинается только после неё.
3. Гейт требует «независимой верификации» и «реальных потребителей» до заморозки, но единственные независимые артефакты — Python-генератор и Rust-oracle, **написанные тем же автором**.
4. **Дешёвое исправление, не требующее новой машинерии:** разделить `#9` на **0.1.0-preview** (`alpha`/`beta` по `RELEASES.md:64-79`) и **0.1.0**. Это одновременно разблокирует гейт «реальный потребитель», займёт ID `ChunkShift` в NuGet и снизит риск.

**Проверенный побочный факт:** `https://www.nuget.org/packages/ChunkShift` → **HTTP 404**; `azuresearch-usnc.nuget.org/query?q=ChunkShift&prerelease=true` → `{"totalHits":0}`. ID свободен на момент проверки (это свидетельство статуса, а не резервирование).

**Минимальный шаг, дающий продукту смысл раньше гейта:** **read-only reuse-report** — `chunkshift plan --base a.csm --target b.csm`, печатающий переиспользованные/отсутствующие байты. Он **не требует нового persisted-формата** (значит, не нарушает отложение CSP в RFC-0003), и все входы уже есть: `ManifestReader` + `UniqueMissingPayloadBytes` из `M0-LAB.md:183-187`.

### 6.2 Отозвано самими исследователями (16 гипотез)

A4 явно опроверг собственные посылки брифинга: «нет прогона тестов на net8.0» (есть — `ChunkShift.Tests.csproj:4`), «heavy-validation только по расписанию» (есть PR-триггер), «нет ARM64/AOT-джобы» (обе есть), «нет Windows ARM64» (`SUPPORT.md:17` — принятая отсрочка), «SHA-pinning/Dependabot отсутствуют» (все `uses:` запинены 40-hex), «golden-фикстуры самоисполняющиеся» (генерация независима; не независим только путь rejection), «история переписана прямыми пушами в main» (PR #30 `merge_commit_sha == 4979bbc` — настоящие squash-merge), «`Thread.Sleep` флейки», «pooled-буферы не очищаются» (документированный контракт `SECURITY.md:44-56`), «проблемы `slnx`/`--no-restore`».

**Мои собственные посылки, опровергнутые исследователями:**
- «`HashSuiteIncrementalHasher` — только для бенчмарков» — **неверно**: это production-код (`CsmInput.cs:80`, `CsmOutput.cs:25`, `ManifestIdAccumulator.cs:37`).
- «Вопрос incremental vs one-shot не решён» — **решён с доказательствами**: `CSM-KERNEL-TOPOLOGY-EVIDENCE-2026-09-23.md:113-125` — BLAKE3 incremental **1,90–2,07× медленнее**; SHA-256 эквивалентен. Осело в PR #48 (`cad3882`), не в #4.
- «Можно убрать копирование, хэшируя инкрементально» — **не работает**: копия существует потому, что **payload обязан быть непрерывным** (замороженный контракт), а не потому что хэш требует целого чанка. Инкрементальный хэш не экономит ни одной копии и стоит 2× на BLAKE3.

### 6.3 Проблемы целостности доказательств (не переиспользовать)

Аудитор A5 при сверке внешних источников обнаружил, что **часть цитат A5 не воспроизводится**:

| Находка | Проблема |
|---|---|

| `A5-F23` | Приписывает `--threshold`, слияние мелких паков и протокол clock-skew lock — **ни одной из этих строк на странице нет**. |
| `A5-F32`, `A5-F34` | Оба неверны относительно собственных docs репозитория: правильные счётчики — **1** (`docs/RELEASES.md:118`) и **0**. |

## 10. Честные ограничения этого отчёта

1. **Ничего не исполнено на C#.** SDK-пин + sandbox на `bin/` блокируют сборку. Все выводы — статическое чтение, документированные измерения репозитория и независимые Python-probe'ы. Верификаторы прошли дальше: они **транскрибировали алгоритм в Python** (225 конфигураций сегментации, fuzz канонизатора на 84 576 вариантов, пересчёт идентичностей всех четырёх фикстур, побайтовое воспроизведение Python-генератора) — но это не то же самое, что прогон настоящего `dotnet test`.
2. **`web_search` недоступен**, PDF не читаются. Часть внешних утверждений A5 не воспроизвелась и помечена в §6.3. Не используйте их.
3. **GitHub-side состояние не проверено:** branch protection, environment reviewers, immutable releases, private vulnerability reporting, опубликованные версии NuGet — всё помечено `UNVERIFIED`. Аудитор A4 подтвердил через REST только один успешный CI-run.
4. **Открытые вопросы, требующие сети или решения владельца:** существует ли SDK `10.0.204` в официальном индексе; валиден ли scope `artifact-metadata: write` в `release.yml:20`; валиден ли runner-лейбл `ubuntu-slim` в `pr-title.yml:13` (если нет — Conventional-Commits-гейт молча не работает); защищён ли `main` и какие проверки обязательны; несут ли issues #6/#8/#9/#17 дополнительные критерии приёмки помимо `PLAN.md` (если да, 25 MISSING — нижняя оценка).
5. **Находки с меткой HYPOTHESIS требуют измерения**, а не действий: прежде всего `A1-F08` (связан ли цикл границ по задержке) — он определяет, стоит ли вообще трогать горячий цикл.
